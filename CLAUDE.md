# Hotel Points Optimizer

## Project overview

A hotel loyalty points optimizer web app. Users add the hotel loyalty programs they belong to (7 US chains -- Hilton, Marriott, Hyatt, IHG, Wyndham, Choice, Radisson -- plus 5 India chains -- Lemon Tree, Sarovar, Taj, Club ITC, Oberoi), type a destination, and get general redemption guidance per chain: roughly how many points a night costs at different property tiers, whether cash or points is the better deal, and what elite perks their tier unlocks. See "India extension" below for how the India chains actually differ from the US model, not just in name.

Mirrors the sibling `Credit Card App Project` (static JSON dataset, no build-time data fetching, Vite + React + `HashRouter`, oxlint, no automated tests) — fully static, no backend. (An earlier version had a small serverless analytics backend counting which chains got selected; it was removed before the analytics were ever wired up to a working Redis instance, since it wasn't needed and added deployment friction — see git history if this is ever revisited.)

**Deliberate scope boundaries** (see the full plan at `~/.claude/plans/i-want-to-build-declarative-twilight.md` for the reasoning):
- No live hotel data, no scraping — hotel loyalty programs prohibit automated access in their ToS and don't offer public APIs for this. All chain data in `app/src/data/chains.json` is hand-compiled and should be spot-checked/refreshed periodically, not treated as live.
- Results are **chain-level general guidance**, never named specific bookable properties — that would require exactly the live-data problem being avoided.
- Membership info entered by a user is **session-only** (in-memory React state via `OptimizerContext`) — no localStorage, no accounts. An account-based "remember me" feature is a possible future addition if there's demand, not built.

## More Hotel Info (`/hotels`)

A reference/browse page, separate from the personalized results flow -- lists all 12 chains grouped by market (`HotelInfoPage.jsx`), each as a collapsed-by-default accordion (`HotelInfoCard.jsx`) showing brand family, a program-type explainer (reuses the same three-way `redemption-chart`/`cashback-currency`/`discount-tier` branch as `ChainResultCard.jsx`, just without any balance-specific numbers since there's no membership context to compute against), and the **full elite tier ladder** (`TierLadder.jsx`) -- every tier's qualification and perks, not just one.

Built for a specific purpose the user stated directly: letting someone see whether a chain's *next* tier is worth chasing before they decide to keep concentrating stays there. If the user already added that chain as a membership (anywhere in the app -- this page reads the same `OptimizerContext` state), `TierLadder` highlights their current tier with a "Your tier" badge, so the "what would I get by moving up" comparison has a concrete starting point. This is a pure read of existing `chains.json` data -- no new data was needed for this page.

**Sub-brand chips are individually expandable (`BrandChip.jsx`)**: each chain's `brandFamily` field changed from `string[]` to an array of `{name, blurb, url}` objects (a breaking shape change -- re-check `grep -rn "brandFamily"` before touching this again). Clicking a chip expands it in place (each chip owns its own `useState`, independent of the chain-level accordion and of every other chip -- multiple can be open at once) to show a one-line positioning blurb plus a `Visit {brand} →` link to that specific sub-brand's own page, not the chain's generic link that already sits at the bottom of the card. Originally built for `/hotels` only, with `ChainResultCard.jsx` (Results page) kept on a plain, non-interactive chip row -- the user later asked for the same treatment there too, so both `HotelInfoCard.jsx` and `ChainResultCard.jsx` now render `<BrandChip>` for every `brandFamily` entry; if a brand chip ever needs a third rendering context, reuse this component rather than reintroducing a plain-`<span>` version. All 60 brands across the 12 chains were researched via web search rather than guessed -- brand positioning and official URLs are public, well-documented information, unlike hidden award-chart pricing, but domains still get renamed/consolidated over time so don't trust this list without spot-checking if it's been a while. Two sourcing wrinkles worth knowing about if this needs updating: (1) several brands (Marriott's Courtyard/Fairfield, IHG's Holiday Inn/Holiday Inn Express, Choice's whole portfolio, Radisson's whole portfolio, all of Sarovar and ITC) don't have their own top-level domain at all -- they're a path on the parent chain's own site (e.g. `choicehotels.com/comfort-inn`), so the link is to that page, not a fabricated separate domain; (2) Wyndham's brand pages exist at both `corporate.wyndhamhotels.com` (franchise/investor-facing) and `wyndhamhotels.com` (consumer booking) -- always use the consumer one, the corporate one is the wrong audience entirely. Sarovar's three sub-brands all point to the same `sarovarhotels.com/about-us/our-brands.html` page since that site has no per-brand landing pages, only per-property ones -- a real limitation of the source, not a bug here.

## Data (`app/src/data/chains.json`)

`{_meta, chains}` shape, one entry per chain with: `id`, `name`, `market` (`"US"` or `"India"`), `currency` (`"USD"` or `"INR"`), `programType` (see "India extension" below -- this is the field that decides which card layout a chain renders with), `accentColor`, `brandFamily`, `eliteTiers` (name/qualification/perks), and `regionPresence` (Strong/Growing/Limited per region -- US chains use the 7 world regions in `app/src/data/regionMapping.js`, India chains use the 7 India-specific regions in `app/src/data/regionMappingIndia.js`; see below for why these are different taxonomies, not just different values).

`programType: "redemption-chart"` chains (the original US model, plus Radisson/Lemon Tree/Sarovar) additionally have `redemptionGuidance` (`pricingModel` + `pointsPerNightByTier` across 4 property-tier buckets: Budget/Midscale, Upscale, Upper Upscale, Luxury) and `pointValuation.valuePerPoint` -- a value in **minor currency units per point** (cents for USD, paise for INR; both are 1/100th of the major unit, so `estimateCashValue()`'s `/100` math is identical either way). This field was renamed from `centsPerPoint` when India chains were added, since "cents" stopped being accurate.

`_meta.disclaimer` is shown on the results page — keep it in sync with reality: this data is hand-compiled and goes stale as programs change terms.

## Outbound booking links

Each chain entry also has a `bookingUrl` — its official top-level hotel-search page (e.g. `https://www.hilton.com/en/search/`). `ChainResultCard.jsx` renders this as a "Search real rooms on {chain}" link (`target="_blank"`, `rel="noopener noreferrer"`), with a hint line naming the user's typed destination so they can search for it themselves once they land on the chain's real site. The user then books directly with their own loyalty account — this app never displays live inventory or availability itself.

**These are deliberately the stable, top-level search pages, not deep links pre-filled with the destination.** I tried to verify real query-parameter formats (e.g. `?destinationAddress.destination=`) via both WebFetch and the Browser pane, and every major chain site (Hilton, Marriott, Hyatt) returned a bot-protection challenge page to both — and the one guess I could test end-to-end (Wyndham's `?query=`) silently returned "0 results" rather than erroring, which would have been a worse experience than no pre-fill at all. A real user's own browser won't hit that wall (it's targeting automation, not people), but there was no reliable way to confirm exact parameter names from here. If you happen to know the correct deep-link format for a chain (e.g. from a bookmarked search URL), it's safe to add it back in and should genuinely improve the hand-off.

## India extension

Added after the user asked for India chain coverage alongside the original US-only 6. Researched real loyalty program names/tiers via web search rather than guessing (sources in the git history's commit for this change) -- Taj Hotels (IHCL) runs **Taj InnerCircle-NeuPass**, Oberoi runs **Oberoi One**, ITC Hotels runs **Club ITC**, plus **Lemon Tree Infinity Rewards** and **Sarovar Rewardz**. **Radisson Rewards** was added at the same time for its large India footprint, but `market` was later corrected to `"US"` -- Radisson Hotel Corporation was founded in Minneapolis, MN in 1962, so despite being added during the India pass it's a US-origin chain, not an India-origin one (see "chain-grouping labels" below). Its `regionPresence` carries both the world-region and India-region taxonomies side by side in one object (flat key lookup, so there's no collision) specifically so it ranks correctly regardless of whether a traveler's `homeMarket` toggle is set to US or India -- the real cost of a chain having genuine multi-region relevance, flagged as a hypothetical during the "should chains have a Global category" discussion and then actually needed here.

**Three `programType`s exist because these programs genuinely don't all work the same way** -- forcing them into the original US "points per night" schema would have meant telling users something false about how their own program works:

- **`redemption-chart`** (Hilton/Marriott/Hyatt/IHG/Wyndham/Choice, plus Radisson/Lemon Tree/Sarovar): the original model. `RedemptionTable.jsx` renders it.
- **`cashback-currency`** (Taj, Club ITC): confirmed both peg 1 point = 1 unit of local currency exactly (1 NeuCoin = ₹1, 1 Green Point = ₹1) and pay out 2-8% of spend depending on tier -- a straight cashback system, not a variable-value points economy with an award chart. There's no "cash vs. points" trade-off to compute, so `ChainResultCard.jsx`'s `cashback-currency` branch shows the peg + exact balance value (`membership.balance` at `valuePerPoint: 100` -- deliberately reusing the same cash-value math as redemption-chart chains rather than a separate code path, since a 1:1 peg is just the range-based math with `min === max`) instead of a points table.
- **`discount-tier`** (Oberoi): confirmed Oberoi One has no points balance at all -- tier (Blue/Silver/Gold/Platinum, confirmed via search) is set by "a proprietary algorithm weighing stay frequency, nights, and spend," and each tier just unlocks a bigger flat discount off the best available rate. No `redemptionGuidance`, `pointValuation`, or `cashbackDetails` on this chain's JSON entry at all -- `MembershipRow.jsx` hides the points-balance input entirely when `chain.programType === 'discount-tier'` (a stray balance value could otherwise sit unused in state with nowhere it renders), and `ChainResultCard.jsx` just shows `chain.discountDetails.note` in place of a points table.

**Data confidence varies by chain, and the JSON reflects that honestly rather than presenting everything with equal certainty**: elite tier *names* are all confirmed from real sources (e.g. Radisson's Club/Premium/VIP three-tier structure, Lemon Tree's Silver/Gold/Platinum/Platinum Plus), but qualification *thresholds* (nights/year) are marked `"(estimate)"` in the JSON wherever the real number wasn't publicly findable -- don't strip that suffix without actually verifying the number. Sarovar Rewardz is the least-documented of the six: only a single "Member" tier is public, so it's modeled with one tier rather than inventing plausible-sounding tier names that would be fabricated, not estimated.

**Currency is per-chain, not toggle-dependent.** Each chain's `currency` field decides its own display (`formatCurrency()` in `pointsLogic.js`, using `Intl`-backed locale grouping: `en-IN` for INR so amounts group as lakhs/crores, e.g. ₹12,34,567, not the US-style ₹1,234,567) -- a USD chain never shows ₹ just because a user's home-base toggle is set to India. This matters: don't wire currency display to the home-market toggle if this is ever refactored, since a chain's real-world currency doesn't change based on where the user happens to be exploring destinations from.

**Region taxonomy differs by market, and this is a second taxonomy, not just different values in the same one.** US chains rank against 7 world regions (`regionMapping.js`); India chains rank against 7 India-specific zones (North/West/South/East/Northeast/Central India, plus "International" -- `regionMappingIndia.js`) because "which world region is this in" is a useless signal for domestic Indian travel (every India-based chain would trivially be "in Asia" for any Indian destination). `matchRegion()` in `pointsLogic.js` takes the keyword map as a parameter (defaulting to the US one) specifically so `ResultsPage.jsx` can pass `INDIA_DESTINATION_KEYWORDS` when `state.homeMarket === 'India'` -- **this wiring is easy to break accidentally**: if a future edit calls `matchRegion(destination)` without checking `homeMarket` again, India destinations will silently stop ranking chains (falls back to "couldn't match region," not a crash, so it's easy to miss in testing). `ChainResultCard.jsx` and `ExplorePage.jsx`'s `chainHintsFor()` both guard against a chain's `regionPresence` simply not having the current region as a key (e.g. a US chain's presence data has no "West India" entry) -- they treat it as "no ranking data" rather than rendering the literal word "undefined."

**The home-base toggle (US/India, on `/explore`) only changes Explore Destinations' hometown dataset and distance unit -- not which chains are selectable.** All 12 chains are always in one unified list in `MembershipsPage`/`MembershipRow.jsx` (grouped into "US-origin chains"/"India-origin chains" `<optgroup>`s for scannability, same grouping in `HotelInfoPage.jsx`), because real travelers can hold both a Hilton and a Taj membership at once; gating the chain picker by a "home base" would've meant hiding one from view depending on an unrelated toggle. The toggle lives in `OptimizerContext` as `homeMarket` (`'US'` | `'India'`) and resets `homeCity` on switch, since a US city string is meaningless against the India dataset and vice versa.

**The chain-grouping labels describe headquarters/origin, not "how global" a chain is** -- originally labeled "United States"/"India" (implying geographic reach), renamed after the user pointed out several India-origin chains have real international footprints too (Oberoi has hotels in Egypt, Mauritius, Indonesia, Morocco; Taj has Maldives, Sri Lanka, UK, Africa). Almost every chain here has *some* cross-border presence, so a "Global vs. regional" split kept producing counterexamples. "Where is this chain headquartered" is a factual, undebatable line instead, so the `market` field's meaning stayed the same (`"US"` | `"India"`) but its display label changed from a geography claim to an origin claim. `regionPresence` (which taxonomy, which regions a chain is actually strong in) is unaffected -- that's the part that already handles "does this chain have relevant hotels near this destination" regardless of category.

**Distance unit and "local" threshold are also market-specific, not just a mi→km conversion.** US mode: miles, `LOCAL_RADIUS_MILES = 250`. India mode: km, `LOCAL_RADIUS_KM = 200` (`distance.js`) -- deliberately not `250 * 1.60934`, since India's road/traffic conditions mean the same straight-line distance often takes longer to drive than the US benchmark this was loosely calibrated to; the India copy also avoids asserting a specific "hours" claim for this reason (just "actual drive time varies a lot with traffic and road conditions") where the US copy says "about a 4-hour drive."

**India's hometown dataset (`app/src/data/indiaCities.js`) is a ~130-city hand-curated list.** Covers every state/UT with at least one city, extra coverage for populous states and popular tourist towns. If a user's town isn't listed, they pick the nearest bigger city instead. Run through the same `preparePlaces()`/`findCity()`/`searchPlaces()` functions as the other two city lists (see "Explore destinations" below) -- same `[name, state, lat, lng]` tuple shape, so no separate code path was needed.

**Grid blowout bug found after publishing, caused by the longer India chain names**: `MembershipRow.jsx`'s row is a CSS grid (`1.4fr 1fr 1fr auto` columns). A `<select>` sizes itself to fit its *widest option*, not just the currently-selected one -- with 12 chains including names like "Lemon Tree Infinity Rewards" and "Taj InnerCircle-NeuPass" alongside short ones like "Club ITC," the closed select's natural width grew past what its grid column had room for. Grid tracks don't shrink a child below its natural content width by default, so the row silently grew wider than the page's 720px max-width and pushed the Remove button out past the visible edge -- reported by the user as "the remove button is out of place" on the published artifact, and not reproducible by just eyeballing it at typical desktop widths where there happened to be enough slack. Fixed with `minmax(0, ...)` on the grid's fractional columns plus `min-width: 0` + `text-overflow: ellipsis` on the select/input themselves, so they shrink to fit and truncate long selected values instead of forcing the row wider. If chain names get longer again in the future (a 13th chain, a rename), re-check this rather than assuming grid `fr` columns handle it automatically -- they don't, for exactly this reason.

## Explore destinations (`/explore`)

A helper reachable from a link on the Destination step ("Not sure where to go? Explore destinations →") for users who don't already know where they're headed. The user picks their hometown from `CityPicker.jsx` (see below); the page sections popular destinations by where they are relative to that hometown, with a "Choose this destination" button on each that sets it as the destination and returns to `/destination`.

**Three destination datasets, sectioned by relationship to the hometown, not by a single "your market's list" like before**: `app/src/data/destinations.json` (US, domestic only), `destinationsIndia.json` (India, domestic only), and `destinationsInternational.json` (everywhere else -- Paris, Tokyo, Singapore, Toronto, etc., ~15 entries). `ExplorePage.jsx`'s `MARKETS` map assigns each home market its own "domestic" list plus the other two as flat sections:
- US hometown: **Domestic Destinations** (US list, split 🚗 Local / ✈️ Worth flying to by the local-radius threshold), **Indian Destinations** (India list, flat), **International Destinations** (flat).
- India hometown: **Domestic Destinations** (India list, split local/flying), **US Destinations** (flat), **International Destinations** (flat).
- International hometown (e.g. Paris): no domestic list exists for arbitrary countries, so it shows **US Destinations**, **Indian Destinations**, and **International Destinations**, all flat -- this also means international hometowns get real recommendations now, not just a "not tuned in yet" placeholder like the first pass of the international-hometown feature had.

Only the home market's own domestic list gets the local/flight split (`classifyDestinations()`); the other two sections use `sortedByDistance()` (same function, called with `radius: 0` so everything lands in `.flight` -- a destination in a different country is realistically never "a local drive," so the split would always be empty/full and add nothing).

**These three lists used to be two, with international spots baked directly into each country's own list** (`destinations.json` had London/Tokyo/Dubai/etc. tagged with world regions; `destinationsIndia.json` had a `region: "International"` tail of its own, overlapping the US list's international entries on things like Dubai and Bangkok). Splitting them out (deduping the overlap) is what made a clean, non-redundant three-section model possible -- each destination now lives in exactly one list.

**International destinations keep their real world-region tag (`Europe`, `Asia`, etc.), not a generic `"International"` placeholder** — this matters for chain hint accuracy (see below).

**Distance is a straight-line (haversine) approximation, not real driving directions** — `app/src/utils/distance.js` computes it from the matched city's coordinates to each destination's. This keeps the feature fully static (no maps/routing API, consistent with the rest of the app's data approach) at the cost of precision — disclosed directly on the page. See "India extension" above for why the US/India markets use different units (mi/km) and thresholds, not a straight conversion; international hometowns default to km.

**A destination essentially at the searched hometown's own coordinates is filtered out** (`classifyDestinations()`'s `distanceValue > 2` filter) — found by testing "Jaipur, Rajasthan" as a hometown when Jaipur is also in the India destinations list: without this, the page recommended Jaipur to someone who just said they live there. Worth re-checking if a future edit touches this filter, since it's easy to not notice in testing unless the searched hometown happens to also be a listed destination.

**Hometown picker (`CityPicker.jsx`)**: a single grouped, custom-styled combobox listing three curated city lists side by side -- 🇺🇸 US Cities (`usCitiesMajor.js`, ~120 major metros), 🇮🇳 Indian Cities (`indiaCities.js`, ~130 cities), 🌍 International Cities (`internationalCities.js`, ~60 major world cities, added on direct request -- Paris, Tokyo, Singapore, etc.). Picking a city commits its label and which group it came from in one action (`CHOOSE_HOME_CITY`), which is how `homeMarket` gets set now -- there's no separate "pick US or India first" toggle anymore, the market is derived from whichever list the chosen city belongs to. All three lists share the same `[name, state, lat, lng]` tuple shape and run through the same `preparePlaces()`/`findCity()`/`searchPlaces()` functions in `distance.js`.

This replaced an earlier version that paired a US/India toggle with a plain `<input list="...">` + native `<datalist>` against the full US Census Gazetteer dataset (`usPlaces.json`, ~31,830 places, lazy-loaded as its own chunk) for exact-match, suburb-level precision (e.g. "Apex, NC"). **The user explicitly chose to trade that precision for a nicer, categorized dropdown UI** -- native `<datalist>` can't be styled or grouped, and a browsable/searchable curated list of major cities was judged more valuable than exhaustive small-town coverage. `usPlaces.json` and its regeneration script (`scripts/parse_gazetteer_places.py`) were deleted; `usCitiesMajor.js` is the ~122-city hand-curated list this project used *before* the Census dataset (recovered from git history, since it was already a well-formed, previously-shipped list, not because it's still described as "not exhaustive" in a way that's newly true -- it always was). If a US town isn't in this list, users pick the nearest bigger metro instead, same as India already worked.

**`homeMarket: 'International'` is safe with `ResultsPage.jsx`'s region-matching**, which only branches on `homeMarket === 'India'` (falling back to the world-region keyword map otherwise) -- `'International'` already gets the same (correct) treatment as `'US'` without any extra code.

If the user already has loyalty memberships added, each destination card also shows a region-relevance hint per membership (e.g. "Hilton Honors (Strong)"), reusing the same `regionPresence` data as the results page -- via `chainHintsFor()`, duplicated in both `ExplorePage.jsx` and `ChainResultCard.jsx`'s caller since it's a few lines each and tied to local component state (`state.memberships`).

**`chainHintsFor()` falls back to a chain's `regionPresence.International` value when the destination's specific region isn't a key it tracks.** World-taxonomy chains (Hilton, Marriott, Hyatt, IHG, Wyndham, Choice) have no `International` key at all, so this is a no-op for them -- they either have the specific region or they don't, same as always. India-taxonomy chains (Taj, Oberoi, ITC, Lemon Tree, Sarovar, and Radisson's dual-taxonomy entry) track their entire overseas footprint as one lump `International` figure rather than per-world-region, so without this fallback they'd show *no* hint at all on the new International Destinations section (or on any US/other-country destination) even though they do publish a real, if broad, "presence abroad" signal. This was worth fixing once the three-section model made it obvious: previously an India chain only ever got a hint on its own domestic India list, which understated what the data actually says.

**The main Destination field (`DestinationInput.jsx`, on `/destination`) also got a grouped dropdown, matching Explore's `CityPicker.jsx` look and reusing the same three curated destination lists** (US/India/International) as its suggestion groups. This is deliberately an *assist*, not a constraint, unlike the hometown picker: the destination field's placeholder literally advertises "rural Montana" as a valid input, and `matchRegion()` does keyword/substring matching against the whole destination string rather than requiring an exact list match -- so the input stays a plain controlled text field the whole time (no internal draft/committed-value split like `CityPicker` needs), and picking a suggestion just fills it in rather than being the only way to set a value. Visual parity comes from literally importing `CityPicker.css` and reusing its class names rather than duplicating the styles.

**These two dropdowns are required to stay aligned, by explicit user instruction -- and they do so structurally, not by convention.** `DestinationInput.jsx` and `ExplorePage.jsx` both import the exact same three files (`destinations.json`, `destinationsIndia.json`, `destinationsInternational.json`) directly -- there is no separate "destination field's list" to fall out of sync, so adding a destination to any of these three files (e.g. the Barcelona/Amsterdam/Berlin/Vienna/Prague/Athens addition to `destinationsInternational.json`) automatically appears in both places with zero extra work. **Do not fork these into page-specific copies for any reason** -- e.g. don't add a "top picks for the destination field" shortlist that duplicates entries instead of reading the shared file, and don't let `DestinationInput.jsx`'s `GROUPS.defaults` (used only for the empty-state quick-picks, capped at 6 per group) drift into a hand-maintained list that isn't just `.find()`-ing names out of the same three files it already imports. If a future request wants the two pages to show *different* destination sets, that's a real design conversation to have explicitly, not something to slide into silently while editing one file.

## Visual design ("scrappy" reskin)

The original theme (warm cream `#faf6ee` background, teal accent, Poppins/Inter pairing, `999px` pill chips, soft drop shadows) was a deliberate v1 default that the user later called out as reading "too AI-generated" -- it matches the exact templated look (soft neutral paper tone, rounded-everything, safe font pairing) that's common across AI-generated pages. Replaced with an "indie-hacker/terminal" look, chosen from three pitched directions (the others were a stark black-and-white brutalist look and a playful zine/scrapbook look):

- **Type**: IBM Plex Mono for all headings/nav/brand (`index.css`), IBM Plex Sans for body copy -- same type foundry so the pairing feels intentional/technical rather than mismatched, replacing the Poppins+Inter combo.
- **Color** (`index.css` `:root` tokens): flat white paper (`--paper: #fff`, no separate "raised" tone), near-black ink (`#111`), and a single loud accent orange (`--accent: #ff5c00`) standing in for the old teal. `--rule`/`--rule-strong` both collapsed to the same near-black value -- there's no longer a "subtle vs. strong" border distinction, borders are just black.
- **Shape**: every `border-radius` in the app was flattened to `0` (except the literal circle on `TierLadder`'s tier dot, `50%`) and every card-defining `border: 1px solid var(--rule...)` was thickened to `2px` -- done as a scripted `sed` pass across all component/page CSS in one go (see git history for this commit if a similar site-wide pass is ever needed again), not by hand-editing each file. `box-shadow` was removed everywhere (`--shadow` token now unused/`none`) -- definition now comes from the bold border instead, not elevation.
- Solid-fill CTA buttons (`.home__cta`, `.chain-result-card__booking-link`, `.hotel-info-card__link`, the multi-step "Next" buttons) each got an explicit `border: 2px solid var(--ink)` added by hand afterward, since the sed pass only touched borders that already existed -- a filled button with `border: none` needed one added, not thickened.
- **Deliberately untouched**: each hotel chain's own `accentColor` in `chains.json` (Hilton blue, Marriott maroon, etc.) -- those are real per-brand colors doing a real job (visually distinguishing chains), not part of the generic "AI-generated" site chrome the user was reacting to.

**Follow-up: flipped to a black background so the orange reads as a real accent, not just a warm one.** All the same tokens in `index.css`, just re-valued for dark: `--paper: #0d0d0d` (page), `--paper-raised: #171717` (cards -- kept a slight step up from the page so cards still read as distinct blocks even though the "real" definition still comes from the 2px border), `--ink: #f5f5f5` (was near-black, now near-white), `--rule`/`--rule-strong` follow `--ink`. `--accent` stayed the same hex (`#ff5c00`) -- orange on black needed zero adjustment to pop, unlike on white. The four semantic soft-tint pairs (`--accent-soft`, `--gold-soft`, `--good-soft`, `--warn-soft` and their matching foreground colors) all got re-picked as dark-bg-appropriate pairs (dark tinted background + a brightened foreground color), not just inverted, since a literal invert of a light pastel is not a usable dark pastel. `color-scheme` flipped from `light` to `dark` so native form-control chrome (date pickers, number spinners) matches without extra CSS.

**This flip broke chain-name-as-accent-colored-text and required a real code change, not just a token swap**: `ChainResultCard.jsx` and `HotelInfoCard.jsx` both rendered the chain name heading with `style={{ color: chain.accentColor }}`. Several real corporate colors are dark (Hilton navy `#104C97`, Oberoi brown `#4A3B2A`, ITC teal `#0D5C4D`) -- chosen for legibility as text on a *white* background, they were chosen for a different actual constraint that no longer holds once the background is black. Fixed by dropping the inline `color` from both headings entirely, so the name just inherits the theme's `--ink` (now white) -- `chain.accentColor` is now used only for the card's `border-left` rail (on `ChainResultCard`; see below for why `HotelInfoCard` no longer uses it there either) and `TierLadder`'s tier-dot fill, never as text.

**The `HotelInfoCard` left-rail went one step further and dropped `accentColor` entirely, per direct user feedback that the stripes "blend in with the background."** The predicted softness for dark corporate colors (Oberoi's brown especially) turned out to be a real, noticed problem, not just a hypothetical -- about half the 12 chains' brand colors are dark/muted enough to read as low-contrast against `--paper-raised` on black. Rather than only fixing the worst offender, `.hotel-info-card`'s `border-left` is now a flat `var(--ink)` (white) for every chain, matching the user's own suggested fix ("put it in white font"). This means the More Hotel Info page no longer shows any per-chain brand color at all -- the chain name and logo-less design already carry the identity, so this was judged an acceptable trade against guaranteed legibility. **`ChainResultCard` (the Results page) still uses `accentColor` for its own left rail and was deliberately left alone** -- the user's feedback named "the More Hotel Info stripes" specifically, and Results' rail wasn't reported as a problem; if the same low-contrast complaint comes up there too, apply the identical fix (drop `accentColor`, use `var(--ink)`).

## Deployment

Live at **https://hotel-points-optimizer.vercel.app**, source at **https://github.com/prabhanjanbalakrishnan/Hotel-Points-Optimizer** (private repo). Deployed following the sibling project's pattern:
1. Created the GitHub repo, pushed this repo directly (`git push -u origin main` — the existing macOS git credential helper handled auth, no `gh` CLI needed).
2. Imported into Vercel with **Root Directory = `app`**.
3. Granting the Vercel GitHub App access needed to be done from GitHub's side directly (`github.com/settings/installations` → Vercel → Configure → add the repo under "Repository access") — the repo didn't show up in Vercel's own import picker until this was done first.
4. Auto-deploy on push to `main` is active (Vercel's default for a GitHub-imported project).
5. Verified: the deep hash route `/#/hotels` loads directly with no server-side rewrite needed — confirmed in-browser.

The analytics backend (Redis-backed `/api/track` + `/api/stats`, a `/stats` page) that originally motivated the "Root Directory = `app`, tiny serverless backend" setup was removed before Upstash was ever configured — it wasn't needed and the unconfigured-backend 500s were pure friction with no upside. The app is now fully static (no `app/api/` at all); Root Directory = `app` is still correct, it's just serving a plain Vite build now.

Neither `gh` nor the `vercel` CLI was available in the environment used for this deploy, and there was no browser session already authenticated to GitHub/Vercel — so repo creation and the Vercel GitHub App permission grant were done manually by the user, everything else (push, verification) was automated.

## Known limitations / next steps

- No automated tests, matching the sibling project's convention. Verified manually via the Browser pane: full membership → destination → results flow (both markets), region-match and no-match cases, mid-flow refresh (correctly redirects to `/memberships` since state is session-only), points/currency math spot-checked against the data, no horizontal overflow at desktop or mobile widths.
- If usage feedback suggests people want their memberships to persist across visits, revisit the "session-only, no accounts" decision — it was deliberate for v1, not a limitation to silently fix.
- All three `CityPicker.jsx` city lists (US/India/International) are curated major-city lists, not exhaustive place data — see "Explore destinations" above for why this was chosen over the exhaustive US Census dataset this project used before. If small-town hometown precision becomes a real complaint, that's the tradeoff to revisit.
- Several India chain data points are explicitly marked `"(estimate)"` in `chains.json` (elite tier qualification thresholds mostly) because the real numbers weren't publicly findable via search — see "India extension" above before treating any India chain's numbers as more solid than the US chains' already-approximate ones.
