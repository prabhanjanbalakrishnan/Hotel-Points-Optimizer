# Hotel Points Optimizer

## Project overview

A hotel loyalty points optimizer web app. Users add the hotel loyalty programs they belong to (7 US chains -- Hilton, Marriott, Hyatt, IHG, Wyndham, Choice, Radisson -- plus 5 India chains -- Lemon Tree, Sarovar, Taj, Club ITC, Oberoi), type a destination, and get general redemption guidance per chain: roughly how many points a night costs at different property tiers, whether cash or points is the better deal, and what elite perks their tier unlocks. See "India extension" below for how the India chains actually differ from the US model, not just in name.

Mirrors the sibling `Credit Card App Project` (static JSON dataset, no build-time data fetching, Vite + React + `HashRouter`, oxlint, no automated tests) — fully static, no backend. (An earlier version had a small serverless analytics backend counting which chains got selected; it was removed before the analytics were ever wired up to a working Redis instance, since it wasn't needed and added deployment friction — see git history if this is ever revisited.)

**Deliberate scope boundaries** (see the full plan at `~/.claude/plans/i-want-to-build-declarative-twilight.md` for the reasoning):
- No live hotel data, no scraping — hotel loyalty programs prohibit automated access in their ToS and don't offer public APIs for this. All chain data in `app/src/data/chains.json` is hand-compiled and should be spot-checked/refreshed periodically, not treated as live.
- Results are **chain-level general guidance**, never named specific bookable properties — that would require exactly the live-data problem being avoided.
- Membership info (and the optional payment-card name, see below) entered by a user is **session-only by default** (in-memory React state via `OptimizerContext`) -- no accounts. There is one deliberate, **opt-in** exception: a "remember on this device" checkbox that mirrors the user's *profile* to this browser's localStorage (see "Remember on this device" below). It is off by default, never sends anything anywhere, and erases on untick.

## More Hotel Info (`/hotels`)

A reference/browse page, separate from the personalized results flow -- lists all 12 chains grouped by market (`HotelInfoPage.jsx`), each as a collapsed-by-default accordion (`HotelInfoCard.jsx`) showing brand family, a program-type explainer (reuses the same three-way `redemption-chart`/`cashback-currency`/`discount-tier` branch as `ChainResultCard.jsx`, just without any balance-specific numbers since there's no membership context to compute against), and the **full elite tier ladder** (`TierLadder.jsx`) -- every tier's qualification and perks, not just one.

Built for a specific purpose the user stated directly: letting someone see whether a chain's *next* tier is worth chasing before they decide to keep concentrating stays there. If the user already added that chain as a membership (anywhere in the app -- this page reads the same `OptimizerContext` state), `TierLadder` highlights their current tier with a "Your tier" badge, so the "what would I get by moving up" comparison has a concrete starting point. This is a pure read of existing `chains.json` data -- no new data was needed for this page.

**Sub-brand chips are individually expandable (`BrandChip.jsx`)**: each chain's `brandFamily` field changed from `string[]` to an array of `{name, blurb, url}` objects (a breaking shape change -- re-check `grep -rn "brandFamily"` before touching this again). Clicking a chip expands it in place (each chip owns its own `useState`, independent of the chain-level accordion and of every other chip -- multiple can be open at once) to show a one-line positioning blurb plus a `Visit {brand} →` link to that specific sub-brand's own page, not the chain's generic link that already sits at the bottom of the card. Originally built for `/hotels` only, with `ChainResultCard.jsx` (Results page) kept on a plain, non-interactive chip row -- the user later asked for the same treatment there too, so both `HotelInfoCard.jsx` and `ChainResultCard.jsx` now render `<BrandChip>` for every `brandFamily` entry; if a brand chip ever needs a third rendering context, reuse this component rather than reintroducing a plain-`<span>` version. All 60 brands across the 12 chains were researched via web search rather than guessed (69 as of Nov 2026, then 72 with the tier work below; Choice had gained the 9 Radisson brands it has owned in the Americas since its 2022 acquisition of Radisson Hotels Americas, each suffixed "(Americas)" where Radisson Rewards still runs the same brand elsewhere -- only `choicehotels.com/radisson` and `/country-inn-suites` were confirmable as brand pages, so the other seven link to Choice's `/about/brands` page rather than guessed URLs) -- brand positioning and official URLs are public, well-documented information, unlike hidden award-chart pricing, but domains still get renamed/consolidated over time so don't trust this list without spot-checking if it's been a while. Two sourcing wrinkles worth knowing about if this needs updating: (1) several brands (Marriott's Courtyard/Fairfield, IHG's Holiday Inn/Holiday Inn Express, Choice's whole portfolio, Radisson's whole portfolio, all of Sarovar and ITC) don't have their own top-level domain at all -- they're a path on the parent chain's own site (e.g. `choicehotels.com/comfort-inn`), so the link is to that page, not a fabricated separate domain; (2) Wyndham's brand pages exist at both `corporate.wyndhamhotels.com` (franchise/investor-facing) and `wyndhamhotels.com` (consumer booking) -- always use the consumer one, the corporate one is the wrong audience entirely. Sarovar's three sub-brands all point to the same `sarovarhotels.com/about-us/our-brands.html` page since that site has no per-brand landing pages, only per-property ones -- a real limitation of the source, not a bug here.

**Brands are tagged with a property tier (`brandFamily[].tier`, `TierExamples.jsx`)**, added after a friend's feedback that the redemption table's "Upscale" / "Luxury" rows meant nothing without examples. Each brand now carries `tier`, one of the four `PROPERTY_TIERS`, and `TierExamples` groups a chain's brands by it (each as a `BrandChip`, so every example still has its blurb and a link to the brand's own site). Shown two ways: a collapsed "What do these tiers look like?" under the redemption table on `redemption-chart` result cards (empty tiers show "No brand in this program sits at this level", because the table has that row and a gap would look like a bug; the flat chip row above it stays), and on `/hotels` as the chain's brand list grouped by tier (empty tiers omitted; all 12 chains). Tier text lives in `TIER_DESCRIPTIONS` (`constants.js`) and the user-facing caveat in `chains.json` `_meta.brandTierNote`.
- **Brands, never named properties**: examples are brand-level, in line with the no-live-data rule; the `Visit {brand}` link is the hand-off to real hotels.
- **Mapping**: industry chain scales onto the app's four buckets (Economy, Midscale, Upper Midscale -> Budget/Midscale; Upscale; Upper Upscale; Luxury). Placements are *typical*, not a guarantee -- award prices are set per property. Sources disagreed on some, so these are judgment calls: **Andaz = Luxury, Kimpton and Hotel Indigo = Upper Upscale** (a Colliers/STR-based brand report; each blurb's own tier word was dropped so it no longer contradicts the label), Crowne Plaza = Upper Upscale (IHG itself files it under "Premium"), voco = Upscale, **Wyndham Garden = Upscale** (one source says midscale), and for IHCL, Vivanta/SeleQtions/Gateway are all Upscale (IHCL groups the three together; a Wikipedia snapshot calls Gateway midscale). Re-check the India chains most -- their tiering rests on looser sources than the US chains'.
- **Three brands were added to fill tiers that had none**: Hyatt Select (Budget/Midscale, launched Feb 2025), Crowne Plaza (IHG, Upper Upscale), Radisson Collection (Radisson, Luxury) -- 72 brands total now. Hyatt Studios was skipped: hyatt.com only has per-hotel pages for it, no brand page to link. Tiers that are genuinely empty (not data gaps): Wyndham Luxury, Lemon Tree and Sarovar Upper Upscale/Luxury, Taj Upper Upscale, Oberoi Budget/Midscale/Upscale.
- All 72 brands have a valid `tier` (checked with a throwaway script). If a brand is added, give it a `tier` -- `TierExamples` silently drops a brand without one.

## Data (`app/src/data/chains.json`)

`{_meta, chains}` shape, one entry per chain with: `id`, `name`, `market` (`"US"` or `"India"`), `currency` (`"USD"` or `"INR"`), `programType` (see "India extension" below -- this is the field that decides which card layout a chain renders with), `accentColor`, `brandFamily`, `eliteTiers` (name/qualification/perks), and `regionPresence` (Strong/Growing/Limited per region -- US chains use the 7 world regions in `app/src/data/regionMapping.js`, India chains use the 7 India-specific regions in `app/src/data/regionMappingIndia.js`; see below for why these are different taxonomies, not just different values).

`programType: "redemption-chart"` chains (the original US model, plus Radisson/Lemon Tree/Sarovar) additionally have `redemptionGuidance` (`pricingModel` + `pointsPerNightByTier` across 4 property-tier buckets: Budget/Midscale, Upscale, Upper Upscale, Luxury) and `pointValuation.valuePerPoint` -- a value in **minor currency units per point** (cents for USD, paise for INR; both are 1/100th of the major unit, so `estimateCashValue()`'s `/100` math is identical either way). This field was renamed from `centsPerPoint` when India chains were added, since "cents" stopped being accurate.

`_meta.disclaimer` is shown on the results page — keep it in sync with reality: this data is hand-compiled and goes stale as programs change terms.

## Outbound booking links

Each chain entry also has a `bookingUrl` — its official top-level hotel-search page (e.g. `https://www.hilton.com/en/search/`). `ChainResultCard.jsx` renders this as a "Search real rooms on {chain}" link (`target="_blank"`, `rel="noopener noreferrer"`), with a hint line naming the user's typed destination so they can search for it themselves once they land on the chain's real site. The user then books directly with their own loyalty account — this app never displays live inventory or availability itself.

**These are deliberately the stable, top-level search pages, not deep links pre-filled with the destination.** I tried to verify real query-parameter formats (e.g. `?destinationAddress.destination=`) via both WebFetch and the Browser pane, and every major chain site (Hilton, Marriott, Hyatt) returned a bot-protection challenge page to both — and the one guess I could test end-to-end (Wyndham's `?query=`) silently returned "0 results" rather than erroring, which would have been a worse experience than no pre-fill at all. A real user's own browser won't hit that wall (it's targeting automation, not people), but there was no reliable way to confirm exact parameter names from here. If you happen to know the correct deep-link format for a chain (e.g. from a bookmarked search URL), it's safe to add it back in and should genuinely improve the hand-off.

## Trip dates and guest/room counts (`TripDetailsInput.jsx`)

Check-in/check-out are native `<input type="date">` fields with `min` attributes (today for check-in, check-in for check-out) -- but **`min` only affects the native calendar widget's styling, it doesn't stop the browser from firing `onChange` with an out-of-range value**. Safari's date picker lets you scroll past `min` in its wheel UI, and typing digits directly into any date input's segments bypasses `min` entirely in every browser -- found via a user bug report where picking a check-in date still let them pick an earlier check-out. The actual fix is rejecting the update in the `onChange` handler itself (`handleCheckInChange`/`handleCheckOutChange`), not just flagging the resulting state as invalid afterward the way `datesInvalid` (still used for the error hint and to disable Next) did alone. Moving check-in to a date on/after the current check-out clears check-out rather than leaving a stale invalid value sitting there silently -- if this pattern (trust `onChange`'s value, validate only after the fact) shows up in a future date/number input, apply the same reject-in-the-handler fix rather than adding another after-the-fact check.

**Guests/Rooms had exactly that pattern, reported separately**: the naive controlled `<input type="number" min="1">` committed `Math.max(1, Number(raw) || 1)` on every keystroke, which snaps back to `1` the instant the field is empty -- i.e. every keystroke where you've backspaced the old value to type a new one, since `Number('') || 1` is `1`. The only way to actually change the number was the spinner arrows/scroll, not typing, which is exactly what the user reported. Fixed with `useCountField()`, a small local hook that keeps its own text buffer (so an empty or transiently-invalid string like `"2."` can sit in the input while the user types) and only pushes a value up to the parent once it parses as a whole number >= 1, cleaning up to a valid integer on blur. Uses the same "adjust local state from a prop during render, not in an effect" pattern as `CityPicker.jsx` to stay in sync when `guests`/`rooms` change externally (e.g. via Back/Next preserving state) without an extra render pass.

## Payment card field (`CardInput.jsx`, `creditCards.json`)

An optional "Card you'll pay with" field on the Destination step (after the trip details). The user either picks from a grouped dropdown (US Cards / Hotel Co-brand Cards / Indian Cards -- 36 cards) or types any card. On Results, each hotel chain the user added gets a note on how that card relates to it. **The card never changes ranking** -- `rankChainsByPresence` is untouched; the region logic keeps sole control of ordering (the user was offered "re-rank chains by card" and picked notes-only).

- **State**: `state.paymentCard`, a plain string written via `SET_TRIP_DETAILS` (no reducer case of its own); `RESET` clears it. Session-only by default (saved only if the user opts into "remember") -- **a card *name* only, never a number**, and the field's hint says so. Home's privacy line mentions "card choice".
- **`CardInput.jsx` is `DestinationInput.jsx`'s pattern on purpose** (controlled free text; suggestions are an assist, not a constraint; imports `CityPicker.css` and reuses its classes so the dropdowns stay visually identical, per the user's standing "keep these dropdowns aligned" instruction). Search also matches `aliases`, so "CSR" finds Sapphire Reserve. Its `GROUPS[].defaults` only `.find()` names out of `creditCards.json` -- same don't-fork-the-list rule as the destination lists.
- **Matching is exact, not fuzzy (`findCard()` in `utils/cardLogic.js`)**, normalized for case/punctuation, against `name` or `aliases`. Same reasoning as `findCity()`: "Amex Platinum" and "American Express Platinum Travel Card (India)" are different cards with different partners, and a close-enough match would silently show the wrong card's notes. An unrecognized string isn't an error -- Results shows one line saying we have no notes on it and the results don't use it.
- **Data shape** (`creditCards.json`): each card has `id`, `name`, `issuer`, `group` (`US` | `Hotel co-brand` | `India`), `aliases`, and `chainLinks: [{chainId, kind, ...}]` where `kind` is `transfers` (`from`/`to` = card points : hotel points, so `{from:1,to:2}` is Amex->Hilton 1:2 and `{from:2,to:1}` is HDFC->Marriott 2:1), `earns-directly` (co-brand cards; optional `detail` replaces the default sentence, used for Tata Neu's NeuCoins), or `status` (`status` = the tier). Any link can carry a `caveat`, shown under the note. Cards with no hotel ties carry a card-level `note` instead, so a matched card is never silent. `describeLink()` builds the displayed sentence. `_meta.disclaimer` is user-facing and shown on Results when a card matched; `_meta.sources` is provenance and is *not* displayed.
- **Results copy rules**: a banner appears only when there's no chain-specific note to show -- unknown card, card with a `note`, or a known card that connects to none of the programs the user added. Otherwise the notes sit on the matching chain cards (after the region hint) and a card's links to chains the user *didn't* add stay hidden (e.g. Sapphire Reserve's IHG status doesn't show if IHG isn't in their memberships). Surfacing "your card also connects to X you haven't added" was deliberately left out.
- **Sourcing, and what was deliberately not claimed.** Started from the sibling Credit Card App Project's `cards.json` (an AI-compiled *draft*: 14 of 21 cards had no hotel partners, ratios were free text, no hotel co-brands, no India cards), then every hotel link was re-verified via web search as of 2026-11-09; the sibling's TD cards were left out. Things that bit during research and are worth knowing before editing: Citi ThankYou->Choice dropped from 1:2 to 1:1.5 in April 2026; Chase->Hyatt is reported to have moved to 4:3 for the Preferred in October 2026 (conflicting, unconfirmed -> caveat on that link only); IHG's October 2026 card refresh means *new* IHG Premier cardholders get Gold, not Platinum (older pages still say Platinum -> caveat); Wyndham's June 2026 refresh changed Earner-card status. **Axis (Atlas/Magnus) are listed with no hotel link at all** because Axis removed and re-added Marriott/Accor/ITC/Hilton across 2026 and sources contradicted each other -- their `note` points users at the Travel EDGE portal instead. Marriott Bonvoy *Bold* (sources disagreed on whether it gives any status) and Choice/Radisson co-brand cards were skipped rather than guessed. HDFC Infinia's non-Marriott hotel transfers (ITC/IHG/Radisson/Wyndham) rest on one secondary source and carry a caveat. Amex India->Hilton 1:1.5 comes from an August 2026 mailer reported by two blogs (caveat). Same standard as the India chain data: only claim what's verifiable, mark the rest.
- **This data goes stale faster than `chains.json`** -- transfer ratios and status perks changed repeatedly within 2026 alone. `_meta.lastUpdated` is the date to check before trusting it; re-verify a card's links before editing them rather than carrying forward the old ones.
- Mobile: the field sits outside `.trip-details-input__row`, so it doesn't interact with that row's known overflow. Verified at 375px: the dropdown panel (longest option: "American Express Membership Rewards Credit Card (India)", wraps to 3 lines), the result notes, and the banner all fit; `.chain-result-card__card-notes li` has `min-width: 0` + `overflow-wrap: anywhere` for the same grid/flex-shrink reason documented under "Grid blowout bug".

## Results summary / "best fit" verdict (`ResultsSummary.jsx`, `utils/verdictLogic.js`)

Added after the user asked what would make the app "actually useful" (the full feature list is in the git history's conversation; this was item #2 of it). The Results page used to be 12 equal-weight cards with no answer; a summary now sits above them: an orange verdict box, a warning when nothing covers the trip, and one clickable row per program (presence chip, what the balance does, a "Covers your trip / Might cover / Falls short" chip when trip dates exist). Clicking a row `scrollIntoView`s that program's card (`ChainResultCard`'s `<article id="result-{membership.id}">`) -- deliberately **not** an `href="#..."` anchor, because `HashRouter` would read it as a route change.

- **`pickVerdict()` rules, in order**: (1) presence at the destination decides first (via `presenceFor()`, the same lookup the ranking and result cards use, so the three can't disagree; each program is rated against whichever region taxonomy it tracks, so the region named in the summary can differ per program -- e.g. Hilton "in Europe" but Taj "in markets outside India" for Paris) -- a program with no hotels near the destination can't be redeemed however big the balance; (2) among programs tied on presence, the bigger balance (in nights covered) breaks the tie; (3) anything still level is returned as a **tie**, never arbitrarily crowned. Returns `null` (and the page shows a nudge instead) with fewer than two programs, or when there's neither a region match nor any balances to separate them. If every chain is `NO_DATA_RANK` for the region (data has nothing to say) presence is treated as non-deciding, same as no region.
- **Balances are compared at one fixed yardstick, `REFERENCE_TIER = 'Upscale'`**, because each chain's chart differs by property tier and comparing "nights covered" needs one tier for all of them. This is stated in the UI copy; if the reference tier ever changes, that copy is built from the constant, so it follows. Only `redemption-chart` chains produce a nights figure -- `cashback-currency` chains show their exact balance value instead and `discount-tier` shows the tier, and neither can win on balance (they can still win on presence).
- **`balanceLeader`**: if a program with *weaker* regional presence has a clearly bigger balance than the winner, the verdict box names it ("X stretches furthest on balance, but has limited presence in Y") rather than silently burying it. Found by testing Choice 200k vs Hyatt 20k in Europe, where the winner (Hyatt, Growing) is the less obvious pick than the balance leader (Choice, Limited).
- **The "none of your balances fully covers N nights" warning** exists because "Best fit" can be a program that still can't pay for the trip (Hilton 80k, Hyatt 30k, 5 nights in Paris: both fall short). Without it the badge implies more than the numbers support.
- All of this is derived from `chains.json` ranges, so it is exactly as approximate as they are; the summary says "rule-of-thumb point ranges, not live prices" rather than claiming precision. `summarizeMembership()`/`pickVerdict()` are pure functions (checked against the real data with a throwaway node script, since the repo has no test runner) -- worth a real test file if more money math gets built on them.
- `PRESENCE_RANK` is now exported from `pointsLogic.js` (it was module-private) so the verdict logic shares the exact same ordering as `rankChainsByPresence`. `summarizeMembership()` takes `resolveDestination()`'s result (`resolved`), not a region string -- this was adapted after the Nov 2026 review-fix PRs replaced `matchRegion`/`rankChainsByRegion` while this feature was being built (see "Destination → region resolution" under the India extension).

## Bank/card points that transfer into hotel programs (`BankPointsSection.jsx`, `transferIn()` in `utils/cardLogic.js`)

Item #3 of the "what would make this actually useful" list. Most points users hold more in bank currencies (Chase Ultimate Rewards, Amex Membership Rewards, HDFC Reward Points...) than in hotel points, and the app already had the transfer ratios (`creditCards.json`) but could only *name* a card. On the Memberships page (below the program list, shown only once at least one program exists) the user can add rows of "card + points balance"; Results then shows what those points become in each hotel program they added and uses that as part of the program's balance.

- **Entry is per *card*, not per points currency.** "50,000 on my Amex Platinum", not "50,000 Membership Rewards". This reuses the already-verified per-card links as-is and -- the deciding factor -- handles HDFC, whose ratios differ by card (Infinia/Diners 2:1 vs Regalia Gold 3:1 to Marriott) and so can't be modeled as one "HDFC points" currency without losing facts. The cost: cards of the same issuer and currency share one pool, so `BankPointsSection` warns when two rows share a `poolKey()` (`issuer|pointsName`) -- "enter the total once, or it's counted twice". Already-used cards are removed from the other rows' dropdowns.
- **Data**: 13 cards got a `pointsName` field (the currency's name, e.g. "Ultimate Rewards"); `transferCards()` = cards with a `pointsName` *and* at least one `transfers` link, so a Freedom or Apple Card can't be picked just to find nothing to convert. (`pointsName` was removed once earlier as unused; it has a real use now. Add it to any new card that has transfer links.) Everything else -- ratios, caveats -- comes from the existing `chainLinks`, so there is still one source of truth and the staleness caveats in "Payment card field" apply unchanged.
- **`transferIn(chainId, bankPoints, cards)`** returns `{sources, total}`; each source keeps the card name, currency, ratio label, converted points and the link's `caveat`, which the result card prints under the line. Converted points are `floor(balance * to / from)` (partial hotel points don't exist); a row with no balance, an unknown card, or no link to that chain contributes nothing. Minimum transfer increments (e.g. some programs only move points in blocks of 1,000) are **not** modeled -- the box says transfers are usually one-way and to check the issuer.
- **The converted total is added to the program's own balance** (`summarizeMembership({transferPoints})`), and `ChainResultCard` computes one `balance = own + transfers.total` that feeds the redemption table, the deal checker, and the cashback-value line, so every number on a card agrees. The summary's rows say "(incl. N from your cards)".
- **Each program is evaluated as if it got *all* of the card points. They can only be spent once**, so a card that transfers to Hilton *and* Marriott shows its full balance under both. This is deliberate (it's the right question -- "if I route everything here, how far does it go?") but would mislead if unlabelled, so it's stated on every transfer box and in the summary footer. Don't "fix" it by splitting balances across programs; that's an allocation problem this app doesn't try to solve.
- **Only programs the user added show transfers**, the same rule as the card notes ("your card also connects to X you haven't added" stays deliberately out). Notably, this is separate from the "Card you'll pay with" field: you can pay with one card and hold points on another; the two share the `creditCards.json` data but not state (`bankPoints` vs `paymentCard`).
- **State**: `state.bankPoints = [{id, cardId, balance}]`, actions `ADD_/UPDATE_/REMOVE_BANK_POINTS`, cleared by `RESET`; session-only unless the user opts into "remember" (bank points *are* part of the saved profile). `parseBalance()` moved to `utils/parseBalance.js` so the program rows and these rows share one rule (blank/negative/non-numeric -> null).
- Verified with a throwaway script against the real data (23 checks: the Amex 1:2, HDFC 2:1 vs 3:1, Citi 1:1.5 floor case, multi-source sums, caveat pass-through, cashback chains, negative balances) and in the browser (both screens, shared-pool warning, removal, Start over, no overflow at 375px).

### Card points on the Destination step, and "Where to send your card points" (`CardPointsInput.jsx`, `PointsPooling.jsx`, `utils/poolingLogic.js`)

A follow-up to the bank-points section, requested by the user: an optional balance field right under "Card you'll pay with", plus a Results block answering "where should I pool these points?".

- **`CardPointsInput` edits the same `state.bankPoints` list as the Memberships page** (one source of truth; a balance entered in either place shows in both, nothing double-counted). `ADD_BANK_POINTS` now accepts an optional `balance`. Clearing the field removes the row (an empty row holds nothing). It's a plain controlled number input like `BankPointsSection`'s, no local text buffer.
- **What it shows depends on the paid-with card**: a `transferCards()` card -> the field; a card sharing a `poolKey()` with a row already entered (Amex Gold after Platinum) -> a note and *no field* (a second row would double-count, and ratios can differ by card within an issuer, e.g. HDFC, so silently reusing the other row would be wrong); a co-brand card (has `earns-directly` links) -> a pointer to that hotel program's own balance, since those points *are* hotel points; anything else (unrecognized, cashback, Axis) -> nothing.
- **The field sits below the card field, not beside it**: card names run to 55 characters and the page is a single narrow column, so side-by-side would not fit at phone width.
- **`buildPooling()`** returns one entry per card balance, each listing the user's *added* programs the card transfers into. Each option goes through the same `summarizeMembership()` as the summary, with only *that card's* points (plus the program's own balance) so the numbers match the summary rows. Ordering and the "Best home" badge reuse the verdict's rules (presence first, then nights covered at `REFERENCE_TIER`, ties shown as ties via `pickVerdict`; cashback chains show a cash value and can't win on balance).
- **Still all-in, deliberately**: each option assumes the whole card balance goes to that one program, and the block says so. Splitting a balance across programs is the allocation problem this app doesn't attempt.
- **One deliberate loosening of the "only programs the user added" rule**: the block ends with one muted line naming programs the card *also* transfers to that the user hasn't added ("add it on the Memberships page to include it here"). They're never ranked. If a card reaches none of the user's programs, the block says so and names the ones it does reach. The per-chain card notes (see "Payment card field") still hide links to un-added chains.
- Verified with a throwaway script (13 checks: Amex 1:2 vs 1:1 ordering, own balance kept separate from transferred points, blank/unknown cards skipped, no-partner case, unresolved destination, ITC cashback via HDFC Infinia) and in the browser (field appears only for transferable cards, shared-pool note, co-brand note, round trip with the Memberships page, clear removes the row, no overflow from the new pieces at 375px).

## Remember on this device (`utils/persistence.js`, `RememberToggle.jsx`)

Item #4 of the "what would make this actually useful" list, and the one deliberate crack in the app's session-only stance -- built **opt-in** so the privacy story stays honest: nothing touches storage until the user ticks the box on the Memberships page (verified: storage is empty before ticking).

- **What's saved is the *profile*, not the trip**: `memberships`, `bankPoints`, `paymentCard`, `homeMarket`, `homeCity`. Destination, dates, guests/rooms and `compareTo` are deliberately never saved -- they're stale by the next visit.
- **Mechanics**: `state.remember` (bool). A `useEffect` in the provider writes the profile whenever it changes *while `remember` is true*, and calls `clearSaved()` whenever it is false -- so unticking erases storage immediately, later edits aren't written, and `RESET` (which sets `remember: false`) forgets everything. Initial state comes from `loadSaved()` via `useReducer`'s lazy initializer, re-seeding the module-level `nextRowId` past the loaded ids so new rows can't collide.
- **Everything read back is untrusted.** `sanitizeProfile()` rebuilds the profile from stored JSON and drops anything that no longer matches the app's data: unknown chains or cards, duplicate programs, tiers that no longer exist, non-numeric/negative balances, Oberoi balances (no points), cards with no transfers; bad markets reset market *and* city together; strings are length-capped; row ids are reassigned. Stored data has a `v` version -- a different version loads as nothing. Tested with 33 assertions including corrupt JSON, hostile shapes and `__proto__` keys.
- **Storage is allowed to be missing.** Every access is try/catch'd (`store()` guards even the `window.localStorage` *getter*, which throws in some privacy modes); `storageAvailable()` makes `RememberToggle` disable itself with an explanation instead of silently not working. A bug found by testing this: `saveProfile()` returned `true` when storage was blocked (an optional-chained call that silently did nothing) -- it now returns true only if it actually wrote.
- **"Start over" becomes "Plan another trip" when remembered** (`NEW_TRIP`: clears destination/dates/guests/rooms/compare, keeps the profile, goes to `/destination`). Without this, the Results page's old "Start over" would have wiped the saved profile -- defeating the feature. When not remembered, the button and `RESET` behave exactly as before.
- Copy that had to change with it: Home's privacy note and closing band ("Nothing saved" would be false for an opted-in user) and the README's "no localStorage" claim.
- A dev-only oddity worth knowing: Vite hot-reload can leave a mounted page holding state from *before* a state-shape change (seen as `bankPoints is not iterable` in the console while building #3). It's an HMR artifact, not reachable in a real load -- `sanitizeProfile` always returns every field.

## Status-chase tracker (`utils/statusLogic.js`, `StatusTracker.jsx`)

Item #5. Each program row on the Memberships page gets an optional "Nights stayed this year"; the result card then shows where that puts them against the program's next tier ("38 nights so far, enough for Silver. Next: Gold at 40, 2 to go. This 4-night trip would get you there (42 nights)") plus the next tier's first three perks.

- **No new data**: thresholds are parsed out of each tier's existing `qualification` string (`"25 nights/yr"`, `"15 nights/yr (estimate)"`, `"100 nights/yr + $23,000 qualifying spend"`) by `tierThresholds()`, so the tracker can only say what `chains.json` already says -- including preserving the `(estimate)` flag (shown in the UI) and flagging a `+ ...` suffix as "plus other requirements". Tiers that don't parse ("Enrollment only", Oberoi's internal algorithm) simply aren't trackable: every chain except Sarovar and Oberoi is.
- **0 is an answer, blank isn't**: `parseNights()` (in `parseBalance.js`) returns `null` for blank/invalid ("not tracking") but keeps `0`, unlike a points balance where 0 and blank mean the same thing. `statusProgress()` returns `null` when `nightsSoFar` is null/undefined, so the tracker is strictly opt-in.
- **Counts nights, not rooms** (programs differ on whether extra rooms count) -- stated in the card's own footnote along with "check your member dashboard", since the app can't see real accounts.
- Changing a row's program clears its nights (same as its balance and tier). The nights field is persisted by "remember" like the rest of the row.
- Verified with 22 assertions on real chain data (exact-threshold edges, 36+4=40 boundary, top tier, Ambassador's `extra`, India `(estimate)` tiers) and in the browser.

## Compare destinations (`ComparePanel.jsx`, `utils/compareLogic.js`)

## "Check a real price" calculator (`DealChecker.jsx`, `evaluateDeal()` in `utils/verdictLogic.js`)

Item #1 of the "what would make this actually useful" list. Each `redemption-chart` result card has a small form: the user types the cash price and points price they saw on the chain's own site for the same room/night, and gets **Use points / Pay cash / Close call**, the value they'd get per point on that booking vs. the chain's typical `pointValuation.valuePerPoint`, the total for their stay, and (if they entered a balance) whether the balance covers it. It exists because the card previously only gave a rule of thumb and left the user to do the division -- and it sidesteps the app's biggest weakness (hand-compiled, approximate numbers) by having the *user* supply the real prices, so no live data is needed. It replaced the "divide the cash rate by the points price" instructions that PR #1 had just rewritten in the rule-of-thumb paragraph; that paragraph now only states the benchmark and points at the calculator.

- **Not shown on `cashback-currency` or `discount-tier` cards**: a 1:1 peg has no cash-vs-points trade-off and Oberoi has no points at all (same reasoning as the existing card branches).
- **The verdict has a ±10% "close call" band (`DEAL_CLOSE_BAND`)**, because the benchmark is a rule of thumb -- calling a 3% difference "use points" would claim precision the data doesn't have. The band edges are inclusive: `evaluateDeal()` rounds the ratio to 6 decimals first, because `$220 / 40,000 points` is exactly +10% but `220/40000*100/0.5` evaluates to 1.0999999... in floating point and was being called "close". Caught by testing boundary values, not by eyeballing; keep that rounding if the math is ever restructured.
- **Units**: `valuePerPoint` is minor units per point (cents/paise), so observed value = `cash / points * 100`. Display goes through the same `¢` / `paise` split as `formatPointValue()`. Cash is labelled in the chain's own currency (`$` or `₹`), not the home-market toggle's, per the standing per-chain-currency rule.
- **Inputs are plain text fields holding strings, parsed only when computing** (`parsePositive()`, strips commas), not controlled numeric coercion -- the same "empty field snaps back" trap the Guests/Rooms fields hit. Clearing, partial input like `12.`, garbage like `abc`, and `1,200.50` all behave (verified in-browser); an incomplete or invalid pair shows a one-line prompt instead of a result.
- **Stay total** multiplies the per-night prices by `nights * rooms` and shows only when that product is > 1. The user enters a *per-room, per-night* price; the verdict itself is independent of nights/rooms (it's a ratio).
- State is local to each card (`useState`), never saved even when "remember" is on, and independent per chain.

## India extension

Added after the user asked for India chain coverage alongside the original US-only 6. Researched real loyalty program names/tiers via web search rather than guessing (sources in the git history's commit for this change) -- Taj Hotels (IHCL) runs **Taj InnerCircle-NeuPass**, Oberoi runs **Oberoi One**, ITC Hotels runs **Club ITC**, plus **Lemon Tree Infinity Rewards** and **Sarovar Rewardz**. **Radisson Rewards** was added at the same time for its large India footprint, but `market` was later corrected to `"US"` -- Radisson Hotel Corporation was founded in Minneapolis, MN in 1962, so despite being added during the India pass it's a US-origin chain, not an India-origin one (see "chain-grouping labels" below). Its `regionPresence` carries both the world-region and India-region taxonomies side by side in one object (flat key lookup, so there's no collision) specifically so it ranks correctly regardless of whether a traveler's `homeMarket` toggle is set to US or India -- the real cost of a chain having genuine multi-region relevance, flagged as a hypothetical during the "should chains have a Global category" discussion and then actually needed here.

**Three `programType`s exist because these programs genuinely don't all work the same way** -- forcing them into the original US "points per night" schema would have meant telling users something false about how their own program works:

- **`redemption-chart`** (Hilton/Marriott/Hyatt/IHG/Wyndham/Choice, plus Radisson/Lemon Tree/Sarovar): the original model. `RedemptionTable.jsx` renders it.
- **`cashback-currency`** (Taj, Club ITC): confirmed both peg 1 point = 1 unit of local currency exactly (1 NeuCoin = ₹1, 1 Green Point = ₹1) and pay out 2-8% of spend depending on tier -- a straight cashback system, not a variable-value points economy with an award chart. There's no "cash vs. points" trade-off to compute, so `ChainResultCard.jsx`'s `cashback-currency` branch shows the peg + exact balance value (`membership.balance` at `valuePerPoint: 100` -- deliberately reusing the same cash-value math as redemption-chart chains rather than a separate code path, since a 1:1 peg is just the range-based math with `min === max`) instead of a points table.
- **`discount-tier`** (Oberoi): confirmed Oberoi One has no points balance at all -- tier (Blue/Silver/Gold/Platinum, confirmed via search) is set by "a proprietary algorithm weighing stay frequency, nights, and spend," and each tier just unlocks a bigger flat discount off the best available rate. No `redemptionGuidance`, `pointValuation`, or `cashbackDetails` on this chain's JSON entry at all -- `MembershipRow.jsx` hides the points-balance input entirely when `chain.programType === 'discount-tier'` (a stray balance value could otherwise sit unused in state with nowhere it renders), and `ChainResultCard.jsx` just shows `chain.discountDetails.note` in place of a points table.

**Data confidence varies by chain, and the JSON reflects that honestly rather than presenting everything with equal certainty**: elite tier *names* are all confirmed from real sources (e.g. Radisson's Club/Premium/VIP three-tier structure, Lemon Tree's Silver/Gold/Platinum/Platinum Plus), but qualification *thresholds* (nights/year) are marked `"(estimate)"` in the JSON wherever the real number wasn't publicly findable -- don't strip that suffix without actually verifying the number. Sarovar Rewardz is the least-documented of the six: only a single "Member" tier is public, so it's modeled with one tier rather than inventing plausible-sounding tier names that would be fabricated, not estimated.

**Currency is per-chain, not toggle-dependent.** Each chain's `currency` field decides its own display (`formatCurrency()` in `pointsLogic.js`, using `Intl`-backed locale grouping: `en-IN` for INR so amounts group as lakhs/crores, e.g. ₹12,34,567, not the US-style ₹1,234,567) -- a USD chain never shows ₹ just because a user's home-base toggle is set to India. This matters: don't wire currency display to the home-market toggle if this is ever refactored, since a chain's real-world currency doesn't change based on where the user happens to be exploring destinations from.

**Region taxonomy differs by market, and this is a second taxonomy, not just different values in the same one.** US chains rank against 7 world regions (`regionMapping.js`); India chains rank against 7 India-specific zones (North/West/South/East/Northeast/Central India, plus "International" -- `regionMappingIndia.js`) because "which world region is this in" is a useless signal for domestic Indian travel (every India-based chain would trivially be "in Asia" for any Indian destination). **Destination → region resolution no longer depends on `homeMarket`** (fixed Nov 2026 after a review found it broken in several ways). `resolveDestination()` in `pointsLogic.js` resolves every destination to *both* taxonomies at once -- `worldRegion` plus, for places in India, `indiaRegion` -- and `presenceFor(chain, resolved)` picks whichever one that chain actually tracks (India zone first, then world region, then an India chain's lump `International` figure for places abroad). `rankChainsByPresence()`, `ChainResultCard.jsx` and `ExplorePage.jsx`'s `chainHintsFor()` all go through `presenceFor()`, so Results and Explore can't disagree. Exact picks from the three destination lists use the `region` already stored on that destination; only free text falls back to keywords, matched as **whole words with the longest keyword winning** -- the old substring match sent Phuket to Europe ("uk"), Indianapolis to Asia ("india"), Romania to the Middle East ("oman") and "South America" to North America ("america"), and with US mode as the default, most US cities and every Indian destination matched nothing. If you add a destination to any list, it resolves automatically; if you want a free-text place to match, add a keyword to `regionMapping.js`/`regionMappingIndia.js`. A quick sanity check is to resolve every listed destination's name and compare against its stored `region` (should be zero mismatches). `ChainResultCard.jsx` and `ExplorePage.jsx`'s `chainHintsFor()` both guard against a chain's `regionPresence` simply not having the current region as a key (e.g. a US chain's presence data has no "West India" entry) -- they treat it as "no ranking data" rather than rendering the literal word "undefined."

**The home-base toggle (US/India, on `/explore`) only changes Explore Destinations' hometown dataset and distance unit -- not which chains are selectable.** All 12 chains are always in one unified list in `MembershipsPage`/`MembershipRow.jsx` (grouped into "US-origin chains"/"India-origin chains" `<optgroup>`s for scannability, same grouping in `HotelInfoPage.jsx`), because real travelers can hold both a Hilton and a Taj membership at once; gating the chain picker by a "home base" would've meant hiding one from view depending on an unrelated toggle. The toggle lives in `OptimizerContext` as `homeMarket` (`'US'` | `'India'`) and resets `homeCity` on switch, since a US city string is meaningless against the India dataset and vice versa.

**The chain-grouping labels describe headquarters/origin, not "how global" a chain is** -- originally labeled "United States"/"India" (implying geographic reach), renamed after the user pointed out several India-origin chains have real international footprints too (Oberoi has hotels in Egypt, Mauritius, Indonesia, Morocco; Taj has Maldives, Sri Lanka, UK, Africa). Almost every chain here has *some* cross-border presence, so a "Global vs. regional" split kept producing counterexamples. "Where is this chain headquartered" is a factual, undebatable line instead, so the `market` field's meaning stayed the same (`"US"` | `"India"`) but its display label changed from a geography claim to an origin claim. `regionPresence` (which taxonomy, which regions a chain is actually strong in) is unaffected -- that's the part that already handles "does this chain have relevant hotels near this destination" regardless of category.

**Distance unit and "local" threshold are also market-specific, not just a mi→km conversion.** US mode: miles, `LOCAL_RADIUS_MILES = 250`. India mode: km, `LOCAL_RADIUS_KM = 200` (`distance.js`) -- deliberately not `250 * 1.60934`, since India's road/traffic conditions mean the same straight-line distance often takes longer to drive than the US benchmark this was loosely calibrated to; the India copy also avoids asserting a specific "hours" claim for this reason (just "actual drive time varies a lot with traffic and road conditions") where the US copy says "about a 4-hour drive."

**India's hometown dataset (`app/src/data/indiaCities.js`) is a ~130-city hand-curated list.** Covers every state/UT with at least one city, extra coverage for populous states and popular tourist towns. If a user's town isn't listed, they pick the nearest bigger city instead. Run through the same `preparePlaces()`/`findCity()`/`searchPlaces()` functions as the other two city lists (see "Explore destinations" below) -- same `[name, state, lat, lng]` tuple shape, so no separate code path was needed.

**Grid blowout bug found after publishing, caused by the longer India chain names**: `MembershipRow.jsx`'s row is a CSS grid (`1.4fr 1fr 1fr auto` columns). A `<select>` sizes itself to fit its *widest option*, not just the currently-selected one -- with 12 chains including names like "Lemon Tree Infinity Rewards" and "Taj InnerCircle-NeuPass" alongside short ones like "Club ITC," the closed select's natural width grew past what its grid column had room for. Grid tracks don't shrink a child below its natural content width by default, so the row silently grew wider than the page's 720px max-width and pushed the Remove button out past the visible edge -- reported by the user as "the remove button is out of place" on the published artifact, and not reproducible by just eyeballing it at typical desktop widths where there happened to be enough slack. Fixed with `minmax(0, ...)` on the grid's fractional columns plus `min-width: 0` + `text-overflow: ellipsis` on the select/input themselves, so they shrink to fit and truncate long selected values instead of forcing the row wider. If chain names get longer again in the future (a 13th chain, a rename), re-check this rather than assuming grid `fr` columns handle it automatically -- they don't, for exactly this reason.

## Explore destinations (`/explore`)

A helper reachable from a link on the Destination step ("Not sure where to go? Explore destinations →") for users who don't already know where they're headed. The user picks their hometown from `CityPicker.jsx` (see below); the page sections popular destinations by where they are relative to that hometown, with a "Choose this destination" button on each that sets it as the destination and returns to `/destination`.

**Three destination datasets, sectioned by relationship to the hometown, not by a single "your market's list" like before**: `app/src/data/destinations.json` (US, domestic only), `destinationsIndia.json` (India, domestic only), and `destinationsInternational.json` (everywhere else -- Paris, Tokyo, Singapore, Toronto, etc., ~15 entries). `ExplorePage.jsx`'s `MARKETS` map assigns each home market its own "domestic" list plus the other two as flat sections:
- US hometown: **Domestic Destinations** (US list, split 🚗 Local / ✈️ Worth flying to by the local-radius threshold), **Indian Destinations** (India list, flat), **International Destinations** (flat).
- India hometown: **Domestic Destinations** (India list, split local/flying), **US Destinations** (flat), **International Destinations** (flat).
- International hometown (e.g. Paris): no domestic list exists for arbitrary countries, so it shows **US Destinations**, **Indian Destinations**, and **International Destinations**, all flat -- this also means international hometowns get real recommendations now, not just a "not tuned in yet" placeholder like the first pass of the international-hometown feature had.

Only the home market's own domestic list gets the local/flight split (`classifyDestinations()`); the other two sections use `sortedByDistance()` (same function, called with `radius: 0` so everything lands in `.flight` -- a destination in a different country is realistically never "a local drive," so the split would always be empty/full and add nothing).

**These three lists used to be two, with international spots baked directly into each country's own list** (`destinations.json` had London/Tokyo/Dubai/etc. tagged with world regions; `destinationsIndia.json` had a `region: "International"` tail of its own, overlapping the US list's international entries on things like Dubai and Bangkok). Splitting them out (deduping the overlap) is what made a clean, non-redundant three-section model possible -- each destination now lives in exactly one list.

**International destinations keep their real world-region tag (`Europe`, `Asia`, etc.), not a generic `"International"` placeholder** — this matters for chain hint accuracy (see below).

**Dublin, Ireland was added (Nov 2026)** to `destinationsInternational.json` (so it appears in both the destination field's dropdown and Explore, per the don't-fork-the-lists rule) -- it was already in the *hometown* picker's `internationalCities.js`, which is a separate list. `dublin` and `ireland` were also added to the Europe keywords in `regionMapping.js` so a destination typed freehand ("dublin") ranks the same as the picked one; before that, typed "dublin" matched no region. Known side effect shared with existing keywords like `paris`: "Dublin, Ohio" also resolves to Europe, because free-text matching is by keyword, not geography.

**Distance is a straight-line (haversine) approximation, not real driving directions** — `app/src/utils/distance.js` computes it from the matched city's coordinates to each destination's. This keeps the feature fully static (no maps/routing API, consistent with the rest of the app's data approach) at the cost of precision — disclosed directly on the page. See "India extension" above for why the US/India markets use different units (mi/km) and thresholds, not a straight conversion; international hometowns default to km.

**A destination essentially at the searched hometown's own coordinates is filtered out** (`classifyDestinations()`'s `distanceValue > 2` filter) — found by testing "Jaipur, Rajasthan" as a hometown when Jaipur is also in the India destinations list: without this, the page recommended Jaipur to someone who just said they live there. Worth re-checking if a future edit touches this filter, since it's easy to not notice in testing unless the searched hometown happens to also be a listed destination.

**Hometown picker (`CityPicker.jsx`)**: a single grouped, custom-styled combobox listing three curated city lists side by side -- 🇺🇸 US Cities (`usCitiesMajor.js`, ~120 major metros), 🇮🇳 Indian Cities (`indiaCities.js`, ~130 cities), 🌍 International Cities (`internationalCities.js`, ~60 major world cities, added on direct request -- Paris, Tokyo, Singapore, etc.). Picking a city commits its label and which group it came from in one action (`CHOOSE_HOME_CITY`), which is how `homeMarket` gets set now -- there's no separate "pick US or India first" toggle anymore, the market is derived from whichever list the chosen city belongs to. All three lists share the same `[name, state, lat, lng]` tuple shape and run through the same `preparePlaces()`/`findCity()`/`searchPlaces()` functions in `distance.js`.

This replaced an earlier version that paired a US/India toggle with a plain `<input list="...">` + native `<datalist>` against the full US Census Gazetteer dataset (`usPlaces.json`, ~31,830 places, lazy-loaded as its own chunk) for exact-match, suburb-level precision (e.g. "Apex, NC"). **The user explicitly chose to trade that precision for a nicer, categorized dropdown UI** -- native `<datalist>` can't be styled or grouped, and a browsable/searchable curated list of major cities was judged more valuable than exhaustive small-town coverage. `usPlaces.json` and its regeneration script (`scripts/parse_gazetteer_places.py`) were deleted; `usCitiesMajor.js` is the ~122-city hand-curated list this project used *before* the Census dataset (recovered from git history, since it was already a well-formed, previously-shipped list, not because it's still described as "not exhaustive" in a way that's newly true -- it always was). If a US town isn't in this list, users pick the nearest bigger metro instead, same as India already worked.

`homeMarket` (including `'International'`) now only affects Explore's hometown dataset and distance unit -- Results ranking doesn't read it at all (see "Destination → region resolution" above).

If the user already has loyalty memberships added, each destination card also shows a region-relevance hint per membership (e.g. "Hilton Honors (Strong)"), reusing the same `regionPresence` data as the results page -- via `chainHintsFor()`, duplicated in both `ExplorePage.jsx` and `ChainResultCard.jsx`'s caller since it's a few lines each and tied to local component state (`state.memberships`).

**`chainHintsFor()` falls back to a chain's `regionPresence.International` value when the destination's specific region isn't a key it tracks.** World-taxonomy chains (Hilton, Marriott, Hyatt, IHG, Wyndham, Choice) have no `International` key at all, so this is a no-op for them -- they either have the specific region or they don't, same as always. India-taxonomy chains (Taj, Oberoi, ITC, Lemon Tree, Sarovar, and Radisson's dual-taxonomy entry) track their entire overseas footprint as one lump `International` figure rather than per-world-region, so without this fallback they'd show *no* hint at all on the new International Destinations section (or on any US/other-country destination) even though they do publish a real, if broad, "presence abroad" signal. This was worth fixing once the three-section model made it obvious: previously an India chain only ever got a hint on its own domestic India list, which understated what the data actually says.

**The main Destination field (`DestinationInput.jsx`, on `/destination`) also got a grouped dropdown, matching Explore's `CityPicker.jsx` look and reusing the same three curated destination lists** (US/India/International) as its suggestion groups. This is deliberately an *assist*, not a constraint, unlike the hometown picker: the destination field's placeholder literally advertises "rural Montana" as a valid input, and `matchRegion()` does keyword/substring matching against the whole destination string rather than requiring an exact list match -- so the input stays a plain controlled text field the whole time (no internal draft/committed-value split like `CityPicker` needs), and picking a suggestion just fills it in rather than being the only way to set a value. Visual parity comes from literally importing `CityPicker.css` and reusing its class names rather than duplicating the styles.

**These two dropdowns are required to stay aligned, by explicit user instruction -- and they do so structurally, not by convention.** `DestinationInput.jsx` and `ExplorePage.jsx` both import the exact same three files (`destinations.json`, `destinationsIndia.json`, `destinationsInternational.json`) directly -- there is no separate "destination field's list" to fall out of sync, so adding a destination to any of these three files (e.g. the Barcelona/Amsterdam/Berlin/Vienna/Prague/Athens addition to `destinationsInternational.json`) automatically appears in both places with zero extra work. **Do not fork these into page-specific copies for any reason** -- e.g. don't add a "top picks for the destination field" shortlist that duplicates entries instead of reading the shared file, and don't let `DestinationInput.jsx`'s `GROUPS.defaults` (used only for the empty-state quick-picks, capped at 6 per group) drift into a hand-maintained list that isn't just `.find()`-ing names out of the same three files it already imports. If a future request wants the two pages to show *different* destination sets, that's a real design conversation to have explicitly, not something to slide into silently while editing one file.

## Visual design ("scrappy" reskin)

The original theme (warm cream `#faf6ee` background, teal accent, Poppins/Inter pairing, `999px` pill chips, soft drop shadows) was a deliberate v1 default that the user later called out as reading "too AI-generated" -- it matches the exact templated look (soft neutral paper tone, rounded-everything, safe font pairing) that's common across AI-generated pages. Replaced with an "indie-hacker/terminal" look, chosen from three pitched directions (the others were a stark black-and-white brutalist look and a playful zine/scrapbook look):

- **Type**: IBM Plex Mono for all headings/nav/brand (`index.css`), IBM Plex Sans for body copy -- same type foundry so the pairing feels intentional/technical rather than mismatched, replacing the Poppins+Inter combo.
- **Color** (`index.css` `:root` tokens): flat white paper (`--paper: #fff`, no separate "raised" tone), near-black ink (`#111`), and a single loud accent orange (`--accent: #ff5c00`) standing in for the old teal. `--rule`/`--rule-strong` both collapsed to the same near-black value -- there's no longer a "subtle vs. strong" border distinction, borders are just black.
- **Shape**: every `border-radius` in the app was flattened to `0` (except the literal circle on `TierLadder`'s tier dot, `50%`) and every card-defining `border: 1px solid var(--rule...)` was thickened to `2px` -- done as a scripted `sed` pass across all component/page CSS in one go (see git history for this commit if a similar site-wide pass is ever needed again), not by hand-editing each file. `box-shadow` was removed everywhere (`--shadow` token now unused/`none`) -- definition now comes from the bold border instead, not elevation.
- Solid-fill CTA buttons (`.home__cta`, `.chain-result-card__booking-link`, `.hotel-info-card__link`, the multi-step "Next" buttons) each got an explicit `border: 2px solid var(--ink)` added by hand afterward, since the sed pass only touched borders that already existed -- a filled button with `border: none` needed one added, not thickened.
- **Deliberately untouched**: each hotel chain's own `accentColor` in `chains.json` (Hilton blue, Marriott maroon, etc.) -- those are real per-brand colors doing a real job (visually distinguishing chains), not part of the generic "AI-generated" site chrome the user was reacting to.

**Follow-up: flipped to a black background so the orange reads as a real accent, not just a warm one.** All the same tokens in `index.css`, just re-valued for dark: `--paper: #0d0d0d` (page), `--paper-raised: #171717` (cards -- kept a slight step up from the page so cards still read as distinct blocks even though the "real" definition still comes from the 2px border), `--ink: #f5f5f5` (was near-black, now near-white), `--rule`/`--rule-strong` follow `--ink`. `--accent` stayed the same hex (`#ff5c00`) -- orange on black needed zero adjustment to pop, unlike on white. The four semantic soft-tint pairs (`--accent-soft`, `--gold-soft`, `--good-soft`, `--warn-soft` and their matching foreground colors) all got re-picked as dark-bg-appropriate pairs (dark tinted background + a brightened foreground color), not just inverted, since a literal invert of a light pastel is not a usable dark pastel. `color-scheme` flipped from `light` to `dark` so native form-control chrome (date pickers, number spinners) matches without extra CSS.

**This flip broke chain-name-as-accent-colored-text and required a real code change, not just a token swap**: `ChainResultCard.jsx` and `HotelInfoCard.jsx` both rendered the chain name heading with `style={{ color: chain.accentColor }}`. Several real corporate colors are dark (Hilton navy `#104C97`, Oberoi brown `#4A3B2A`, ITC teal `#0D5C4D`) -- chosen for legibility as text on a *white* background, they were chosen for a different actual constraint that no longer holds once the background is black. Fixed by dropping the inline `color` from both headings entirely, so the name just inherits the theme's `--ink` (now white) -- `chain.accentColor` is now used only for the card's `border-left` rail (on `ChainResultCard`; see below for why `HotelInfoCard` no longer uses it there either) and `TierLadder`'s tier-dot fill, never as text.

**The `HotelInfoCard` left-rail went one step further and dropped `accentColor` entirely, per direct user feedback that the stripes "blend in with the background."** The predicted softness for dark corporate colors (Oberoi's brown especially) turned out to be a real, noticed problem, not just a hypothetical -- about half the 12 chains' brand colors are dark/muted enough to read as low-contrast against `--paper-raised` on black. Rather than only fixing the worst offender, `.hotel-info-card`'s `border-left` is now a flat `var(--ink)` (white) for every chain, matching the user's own suggested fix ("put it in white font"). This means the More Hotel Info page no longer shows any per-chain brand color at all -- the chain name and logo-less design already carry the identity, so this was judged an acceptable trade against guaranteed legibility. **`ChainResultCard` (the Results page) still uses `accentColor` for its own left rail and was deliberately left alone** -- the user's feedback named "the More Hotel Info stripes" specifically, and Results' rail wasn't reported as a problem; if the same low-contrast complaint comes up there too, apply the identical fix (drop `accentColor`, use `var(--ink)`).

**Home page redesign (`Home.jsx`/`Home.css`)**: the original home was a centered headline, paragraph, and one button -- the user asked for it to be "more aesthetic and more lively." Kept entirely inside the existing system above (same tokens, Plex Mono/Sans, square corners, 2px borders; no new colors, no gradients). What it has, top to bottom: a left-aligned hero (orange highlight-marker on "points," faint dot-grid backdrop) beside a **live terminal card**; a scrolling orange strip of all 12 program names; a stats row; a three-step "How it works"; and a solid-orange closing CTA band.
- **The terminal demo is real data, not hand-written sample output.** `DEMOS` in `Home.jsx` is computed at module load from `chains.json`: for each of four hardcoded destination/region pairs (Tokyo/Asia, Paris/Europe, Dubai/Middle East, Goa/West India) it filters chains whose `regionPresence[region] === 'Strong'` and shows each one's `pointValuation.valuePerPoint` (or "1 pt = ₹1" for `cashback-currency`, "tier discounts" for `discount-tier`). If `chains.json` changes, the demo changes with it -- don't replace this with static strings. Goa/West India is deliberately in the rotation so India chains and the cashback label get shown, not just US ones.
- **The stats row is computed too** (`chains.length`, summed `brandFamily` lengths, summed lengths of the three destination JSONs), so it can't drift from the datasets -- adding Spain cities to `destinationsInternational.json`, for instance, bumps the "destinations to explore" number automatically. The "0 accounts to create" tile is a hardcoded fact about the app's design (session-only, no accounts), not a computed one.
- **Motion is CSS-only except the demo's rotation timer** (a single `setInterval` advancing an index; `key={index}` on the terminal body remounts it so the typing/row-reveal CSS animations replay). Every animation's *base* style is the finished state and the keyframes only define `from`, so with `prefers-reduced-motion: reduce` (which sets `animation: none` under `.home`) the page just shows the completed state, and the effect also skips starting the timer. The reduced-motion marquee is a second case worth knowing about: the animated version is a duplicated list translated `-50%`, so with animation off it has to stop being a one-row clipped strip -- it wraps on wide screens and becomes a single swipeable row (`overflow-x: auto`) at <=860px, where wrapping would turn it into a ~300px slab of orange. Both were found by testing the real shipped media rules rather than assuming; the first version of the wrap fallback didn't actually wrap (`flex-shrink: 0` on the list) and showed 1 of 12 names.
- **Hover-only hard shadows are a deliberate, narrow exception to the "no `box-shadow` anywhere" rule above**: the primary CTA and the how-it-works step cards get an offset solid shadow (`4px 4px 0` / `5px 5px 0`) plus a `translate(-2px,-2px)` lift on hover only -- a neo-brutalist "button pressing" cue that suits the scrappy look and doesn't reintroduce soft elevation at rest. Don't generalize it into resting-state card shadows.
- **The hero's three links are structured as one primary button on its own row plus a pair of outline links beneath it**, on purpose: at the 1080px max width the copy column is only ~517px, and all three on one line need ~633px, so a flat flex-wrap left "Browse the programs" orphaned alone on a second row. The tops-of-boxes row count is a misleading way to check this (different button heights + `align-items: center` means tops differ even on a shared row) -- compare vertical *centers*.

## Deployment

Live at **https://hotel-points-optimizer.vercel.app**, source at **https://github.com/prabhanjanbalakrishnan/Hotel-Points-Optimizer** (private repo). Deployed following the sibling project's pattern:
1. Created the GitHub repo, pushed this repo directly (`git push -u origin main` — the existing macOS git credential helper handled auth, no `gh` CLI needed).
2. Imported into Vercel with **Root Directory = `app`**.
3. Granting the Vercel GitHub App access needed to be done from GitHub's side directly (`github.com/settings/installations` → Vercel → Configure → add the repo under "Repository access") — the repo didn't show up in Vercel's own import picker until this was done first.
4. Auto-deploy on push to `main` is active (Vercel's default for a GitHub-imported project).
5. Verified: the deep hash route `/#/hotels` loads directly with no server-side rewrite needed — confirmed in-browser.

The analytics backend (Redis-backed `/api/track` + `/api/stats`, a `/stats` page) that originally motivated the "Root Directory = `app`, tiny serverless backend" setup was removed before Upstash was ever configured — it wasn't needed and the unconfigured-backend 500s were pure friction with no upside. The app is now fully static (no `app/api/` at all); Root Directory = `app` is still correct, it's just serving a plain Vite build now.

Neither `gh` nor the `vercel` CLI was available in the environment used for this deploy, and there was no browser session already authenticated to GitHub/Vercel — so repo creation and the Vercel GitHub App permission grant were done manually by the user, everything else (push, verification) was automated.
